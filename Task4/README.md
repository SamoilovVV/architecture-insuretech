# Задание 4. Проектирование продажи ОСАГО
Не смотря на то, что продажа ОСАГО внешне похожа на продажу страхования жизни, в реальности это совсем другой продукт, который требует другой процедуры обработки. Это связано с тем, что ОСАГО более востребовано на рынке, а условия и предложения страховых меняются значительно более динамично. Частота запросов к страховым при этом сильно возрастает, поэтому использование ins-product-aggregator нецелесообразно, так как может привести к его значительной перегрузки. Пользователь ожидает, что сможет получить предложения нескольких страховых с учётом индивидуальных условий за приемлемое время (не более 2-3 минут), что накладывает специальные требования на обработку этого вида страховых продуктов.

В связи с этим, для сервиса osago-aggregator целесообразно иметь отдельную БД (osago-aggregator-db).
Отправка заявок на ОСАГО может осуществляться по "старому" через REST API, но для динамического получения данных и обновления экана ожидания предпочтительно использование паттерна **Server push** (взаимодействие front-to-back) по технологии **SSE** (Server sent events).
Для взаимодействия core-app с osago-aggregator организуются отдельные очереди для заявок на ОСАГО и предложений по ОСАГО для обеспечения асинхронности запросов.

В связи с ожидающимся ростом нагрузки целесообразно использование паттернов **Rate Limiter** и **Timeout** для взаимодействия веб-приложения и core-app для снижения нагрузки и предотвращения DDOS-атак. Для взаимодействия osago-aggregator c внешними сервисами страховых компаний могут быть применены паттерны **Timeout**, **Circuit Breaker** и **Retry** для снижения уровня неудачных запросов и повышения отказоустойчивости системы в целом.
